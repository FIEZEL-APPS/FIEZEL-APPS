# FIEZEL m025 Audit Ledger — Neural Voice + Puter Authentication

Status: investigation artifact only; no production source changed on this branch at creation time.

Baseline commit: `708f3b4376b225b9fbe8f988d6c78844bb22f403` (`Deploy m024 neural timeout phase hotfix`)

Date: 2026-08-15 (Asia/Jakarta)

## Executive finding

Two independent device failures are present on the m024 baseline.

1. Neural voice remains capable of reporting `neural_tts_timeout` after assets are fully cached because the current 30-second timeout still wraps the complete `local.speak()` promise. `local.speak()` includes both model generation and `await playback.done`, so the budget is not an inference-only budget.
2. Puter login can loop indefinitely on the affected Apple PWA because the service worker gives the document `Cross-Origin-Opener-Policy: same-origin` while the device reports `crossOriginIsolated === false`. In that state Puter.js uses popup + `postMessage` authentication. COOP `same-origin` makes a cross-origin auxiliary browsing context appear closed to the opener, so a popup may visibly complete login without returning/adopting the token in the FIEZEL PWA. The next `puter.workers.exec()` sees no `authToken` and launches authentication again.

The current Quality Gate can stay green while both problems exist because its m024 neural timeout gate is predominantly source-structure verification and the COOP test does not exercise the Puter popup/token-return contract.

## Evidence ledger

### N-001 — Neural assets are not the primary failure

Observed device diagnostics from m024 show the neural assets prepared/cached while the runtime later falls back with `neural_tts_timeout`. The investigation therefore treats model download/quota as already-cleared prerequisites unless a new device dump contradicts them.

Repo evidence:

- `features/neural-voice/fiezel-neural-voice-bootstrap.js` maintains separate prepared/cache state from initialized/ready state.
- Apple standalone policy already forces WASM single-thread + proxy behavior.

Conclusion: do not restart the investigation from model download unless cache verification fails explicitly.

### N-002 — m024 timeout is still wider than generation

`fiezel-neural-voice-bootstrap.js` waits for `initialize()` first, then races `local.speak(...)` against `NEURAL_TTS_TIMEOUT_MS`.

`features/neural-voice/fiezel-neural-voice.js` implements `local.speak()` as:

1. `adapter.generate(...)`
2. `playAudio(...)`
3. `await playback.done`
4. only then resolve `speak()`

Therefore the current `NEURAL_TTS_TIMEOUT_MS` measures generation + playback + related service overhead. A long but valid playback can be classified as `neural_tts_timeout`.

Severity: HIGH.

Recommended m025 direction: put the timeout immediately around each `adapter.generate()` call inside the voice service and remove the outer full-speak race from bootstrap.

### N-003 — m024 stage diagnostics are being truncated by audibility patch

Bootstrap and core voice diagnostics retain up to 200 records. `fiezel-neural-voice-audibility-fix.js` writes to the same localStorage key but truncates the merged list to the last 30 records.

Effect: newly-added m024 events such as `init_start`, `init_ready`, `speak_init_ready`, `speak_generate_start`, `generate_start`, `generate_ready`, `playback_start`, and `playback_done` can be deleted after browser fallback activity.

Severity: HIGH because it destroys the evidence needed to distinguish generation stall from playback stall.

Recommended m025 direction: one shared retention target of at least 200 records; never let a patch writer lower the retention of the common diagnostics stream.

### P-001 — Puter implicit auth is triggered by workers.exec when token is absent

FIEZEL AI calls `puter.workers.exec()` through `coreWorkerExec()`.

Current Puter.js `WorkersHandler.exec()` invokes `#authenticateIfNeeded()` first. In web mode, if `puter.authToken` is empty, it calls `puter.ui.authenticateWithPuter()`.

Therefore any failure to adopt/persist the popup token naturally reproduces this loop:

`ask AI -> workers.exec -> auth popup -> popup appears successful -> token absent in FIEZEL -> ask AI -> workers.exec -> auth popup -> ...`

### P-002 — Puter login transport differs by crossOriginIsolated state

Current Puter.js `Auth.signIn()` has two relevant paths:

- when `window.crossOriginIsolated === true`, it can poll `/login/wait` using a sign-in session;
- when `window.crossOriginIsolated === false`, it relies on the popup returning a `puter.token` message to the opener and validates `event.origin`, `event.source`, and `msg_id`.

The affected FIEZEL device reports `crossOriginIsolated === false`, so the popup-message path is the active contract.

### P-003 — FIEZEL COOP policy conflicts with that non-isolated popup path

Current `sw.js` injects:

`Cross-Origin-Opener-Policy: same-origin`

and:

`Cross-Origin-Embedder-Policy: credentialless`

The HTML Standard specifies that COOP `same-origin` additionally requires auxiliary browsing contexts to stay same-origin with the same opener policy; otherwise the auxiliary context appears closed to the opener. This is exactly the dangerous configuration for a cross-origin Puter authentication popup when the page did not actually become cross-origin isolated.

Puter's cross-origin-isolated fallback cannot help on the affected device because the device reports `crossOriginIsolated === false`.

Severity: CRITICAL for AI usability.

Recommended m025 direction:

- On affected WebKit documents, use `Cross-Origin-Opener-Policy: same-origin-allow-popups` so the Puter authentication auxiliary context can retain the opener relationship.
- Keep the existing `same-origin` policy on engines where FIEZEL successfully enters a cross-origin-isolated mode and Puter can use its isolated sign-in flow.
- Do not intercept/proxy `https://js.puter.com` in the service worker.

### P-004 — Do not build a large auth logging subsystem first

The root mechanism is already identifiable from FIEZEL + Puter source. m025 should add only a safe auth snapshot to Diagnostics so the physical-device fix can be verified without exposing credentials.

Safe fields:

- `puterLoaded`
- `puterWorkersLoaded`
- `puterEnv`
- `puterAuthTokenPresent` (boolean only)
- `puterIsSignedIn` (boolean only)
- `puterStoredTokenV2Present` (boolean only)
- `puterStoredTokenOrigin`
- `puterApiOrigin`
- `puterDefaultGuiOrigin`

Never export the auth token itself.

## Quality-gate gap

Current `.github/workflows/quality.yml` runs neural tests and `sw-corp-test.js`, but:

- syntax checking is root-only (`*.js`, `*.mjs`), not recursive;
- `neural-voice-timeout-phase-test.js` verifies source ordering and expected strings, not the runtime behavioral distinction between generation time and playback time;
- `sw-corp-test.js` verifies third-party Puter traffic is not reconstructed, but does not verify popup-compatible COOP behavior for WebKit;
- no regression test seeds >30 neural diagnostic records and ensures audibility writes preserve them.

## Promotion gates

m025 must not be considered fixed merely because CI is green. Promotion requires all of the following:

1. Exact-head Quality Gate success.
2. PWA diagnostics reports build `m025-1` and active service worker revision m025.
3. Puter: one completed login produces `puterAuthTokenPresent=true` and a second AI request does not reopen login.
4. Neural test: diagnostics retain init/generate/playback stage events after the test completes.
5. Neural success path: at least one physical-device neural test reaches `generate_ready`, `playback_start`, and `playback_done`, and does not report `neural_tts_timeout` solely because playback exceeds the generation timeout.
6. If generation truly exceeds the configured generation timeout, the event/reason must be explicitly generation-specific, not an ambiguous whole-speak timeout.
